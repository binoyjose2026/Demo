URL Shortener — v2 Scalability Design Review

A scoped, deep review of what it takes to run this C#/.NET 9 URL shortener at extreme scale — 28 numbered consideration documents covering the create path, storage, caching, messaging, resilience, security, infrastructure, and forward-looking AI readiness.

Overview & Scale Assumptions

This review is deliberately scoped to one topic: scalability. Security posture in general, cost, and team process are explicitly deferred to a later pass — scalability alone is a big enough topic to go deep on first. The review was commissioned against a specific, believable-but-not-hyperscale load target, chosen because the trade-offs at that scale actually matter — not a toy example, not a hyperscale fantasy.

Creates today
1,000,000 / day
Creates in 5 years
5,000,000 / day
Fetches today
10,000,000 / day
Fetches in 5 years
100,000,000 / day

That is roughly 5x growth over 5 years on both sides — fetches always outweigh creates by an order of magnitude or more, because a link is created once and clicked many times. At the 5-year horizon, average sustained load works out to roughly 58 creates/sec and ~1,160 fetches/sec, with realistic peak multipliers of 5–10x pushing fetch bursts toward 6,000–12,000/sec. Every numbered document in this review designs against that peak-load future, not the comfortable average.

Every document below is explicitly framed as an architectural exploration — what extreme scale would require — not a claim that v1's simpler choices (SQLite, IMemoryCache, in-process channels) were mistakes for their context. Several documents conclude that a popular, "obvious" technology (Kafka, the Outbox pattern, the Saga pattern) is not justified at this system's actual numbers, and say so plainly with the math to back it up rather than defaulting to industry-standard advice.

Create-Path & Data Layer

How a single POST /api/short-urls stays cheap, collision-free, and safely retryable once it's served by a horizontally-scaled fleet writing billions of rows over five years — and which distributed-systems patterns (Outbox, Saga) turn out not to be needed at all.

Doc 01Overview / Framing

Create-Path Extreme Scalability

Question: Why does v1's SQLite + IMemoryCache design hit a wall at 5M creates/day, and what does the create path need to look like instead?

Decision: Three specific bottlenecks stop being theoretical at this scale: SQLite's single-writer file lock, no horizontal scale-out of the database tier, and per-instance cache staleness that compounds as fleet size grows. The fix is pre-allocated ID blocks (10,000 IDs per instance, one allocator round-trip per block) with a reversible bit-mixing/permutation step before base62 encoding — so IDs are collision-free by construction (not by low probability) while still satisfying ANFR-08's non-enumerability requirement. The primary datastore moves to a server RDBMS with read replicas and/or sharding; downstream work (analytics indexing, cache warm, moderation re-check) is decoupled from the synchronous create response via asynchronous event publication.

Key numbers
  • Block size: 10,000 IDs per instance — a ~4-order-of-magnitude reduction in allocator contention vs. a per-request uniqueness check.
  • Cumulative created links approach ~9 billion over the 5-year horizon at 5M/day.
Alternative considered
Snowflake-style local ID generation (timestamp + machine ID + sequence) is named as the fallback if the block allocator itself becomes the bottleneck — not adopted as primary because it needs a reliable machine-ID assignment mechanism and produces a longer encoded code.

What doesn't need to change: the API layer's horizontal scaling story carries forward unchanged from v1 — controllers and services are already stateless. What must move to a shared store: per-caller rate-limit counters (see Doc 12).

Doc 10Late-stage escalation, not day-one

Database Partitioning / Sharding

Question: Does the core ShortUrl table need sharding at this scale, and if so, on what key?

Decision: Partition key: a stable hash of the short Code — not creation date (that's right for the click-event log, wrong here, since a redirect request only ever carries a code, never a date) and not the raw pre-obfuscation integer ID (would correlate sequential blocks onto adjacent hash values). Topology: consistent hashing with virtual nodes, starting at ~4 physical shards mapped onto 128–256 virtual nodes, specifically because adding a shard only moves ~1/N of the data instead of a full range re-split.

When to actually shard: not at the start of the 5-year horizon. Escalation order: (1) migrate off SQLite to a server RDBMS with read replicas, (2) apply native single-database table partitioning, (3) shard only once sustained peak writes exceed ~2,000–3,000 writes/sec, or backup/maintenance windows breach the operational SLA, or a genuine multi-region active-write need emerges. This review's own numbers (~58 creates/sec average, hundreds-to-low-thousands at peak) land inside what a single well-tuned primary absorbs for most of the horizon.
Real costs, named honestly
  • Cross-shard queries (e.g., "list all links for this department") become scatter-gather or need a secondary index.
  • Cross-shard transactions lose single-database ACID — the design leans on not building features that need them, not solving distributed transactions.
  • Operational load multiplies by shard count: N backups, N migrations, N connection pools.

Custom-alias uniqueness checks and the create/redirect hot paths stay exactly as cheap as an unsharded table, since the code itself is the routing key.

Short-Key Generation: Survey and Comparison

Question: Across every realistic short-code generation approach, does pre-allocated ID blocks (Doc 01's pick) actually win, with real collision math?

Decision: Yes — confirmed, not revised, across 7 surveyed options. The birthday-paradox math is the load-bearing evidence: v1's random-generation-with-retry approach is fine at 10M links (~1 in 350,000 per-attempt collision probability) but degrades to a real, measurable tax at this review's 5-year cumulative volume of ~9 billion links (~1 in 390 per-attempt collision probability — roughly 5 retried requests/sec at 2,000 creates/sec peak).

Idempotency-Key Support for Create Short URL

Question: What happens when a client retries a create request after a lost response, once retry-with-backoff is the standard resilience pattern?

Decision: Client-generated Idempotency-Key GUID header, one per logical attempt (reused across every retry). Server computes a SHA-256 hash of the canonicalized request body; on a replay with a matching hash, it returns the original stored response verbatim with no new row created; on a matching key with a different body, it returns 409 Conflict (not 422, which is reserved for the malicious-URL policy check).

Even a conservative 0.1–0.5% retry rate against 1M–5M creates/day is 1,000–25,000 duplicate-intent creates per day with no protection. 24 hours (not 15 minutes, not 30 days) is chosen to cover realistic outer-retry-loop scenarios (batch jobs, offline clients) while keeping storage small — the same window Stripe documents for the same reasoning.

Real cost, named honestly
An in-flight race between two near-simultaneous retries needs an atomic SET NX-style reservation, not just a lookup — naive check-then-act lets both proceed and defeats the whole mechanism. Every protected create also pays 1–2 extra Redis round trips, and callers that never send the header get no protection at all (a deliberate trade-off, not an oversight).

Do We Need the Outbox Pattern?

Question: Once the create path publishes a UrlCreated event, do we need the Outbox pattern to guarantee the DB write and the event publish don't diverge (the dual-write problem)?

Verdict: No — not for UrlCreated at this system's scale, with one narrow exception. The core ShortUrl row is a single local database write with no broker involved — it was never exposed to the dual-write problem in the first place. The only thing that can be lost is the event, and what a missed event costs is a missed index entry / stale search result — self-healing on the next read, correctable by a periodic RowVersion-driven reconciliation sweep that's needed either way (Outbox only guarantees the message left the service, not that a consumer processed it).

The narrow exception: if a future event drives something with real consequence when missed — a billing/quota debit, a provable compliance/audit event — that event should go through Outbox. UrlCreated as scoped (analytics/search/cache) is not that.

If the exception ever applies

The document fully designs the mechanism for reference: an OutboxMessage table (same audit/RowVersion conventions as every other table) written in the same transaction as the entity, and a polling relay (not CDC/Debezium — SQLite has no log-streaming support, and even the server-RDBMS escalation path doesn't justify standing up Kafka Connect for this volume).

Doc 29Not adopted

Why the Saga Pattern Is Not Needed for URL Creation

Question: Is Saga-style compensating-transaction coordination needed for the create flow, since it's "not business critical"?

Verdict: No. Sagas exist to keep multiple independently-owned databases consistent when a later step fails after earlier steps already committed elsewhere (the canonical flight+hotel+payment example — a seat is held, a room is blocked, and the payment fails, leaving real-world resources needing compensation). URL creation is one write, one database, one atomic commit — there is no second service, no partial-success state, and nothing to compensate. The one thing outside that transaction, the UrlCreated event, is fire-and-forget and depended on by nothing downstream — calling it a Saga step would be a category error, not a scale judgment.

Cost of adopting anyway: orchestration/choreography machinery with nothing real to coordinate, compensating-transaction logic for a failure mode that doesn't exist (or, worse, inventing artificial intermediate states purely to give the Saga something to compensate), and new operational surface area — all for zero correctness benefit.

When it would flip
A genuinely hypothetical future example: a "custom domain provisioning" feature that reserves a domain in one service and notifies billing in another, each with its own datastore — that has the real Saga shape. Nothing in v1/v2 introduces this today.

Doc 03Adopted — polyglot split

Elasticsearch vs. SQL Server for the Click/Analytics Event Store

Question: Is Elasticsearch genuinely better for the click-event store at this scale, or is that just reflexive "ES is for big data"?

Decision: Polyglot persistence, explicit split — Elasticsearch for the click/analytics event store, SQL Server (or its server-RDBMS successor) stays the relational system of record for the core ShortUrl mapping. The workload shapes are opposite: the mapping table is small, transactional, and correctness-critical (exactly what a relational engine is built for); the event store is huge (up to 100M events/day → 9–36.5 billion rows over a 90–365 day retention window), append-only, near-zero update rate, and aggregation-heavy over time ranges — exactly Elasticsearch's design target.

Doc 04Elasticsearch, conditionally

Elasticsearch vs. MongoDB for Analytics Events

Question: Given the same click-event workload, does MongoDB beat Elasticsearch on its own terms?

Decision: Elasticsearch, but stated as a genuine conditional, not a unilateral win. MongoDB's native TTL indexes solve v1's open retention question with near-zero implementation cost, and its aggregation pipeline is adequate at moderate scale. But ES's aggregation engine (purpose-built doc_values + date_histogram/terms) degrades far less as cardinality grows, its ILM is a closer match to "we don't know the retention window yet, but apply it uniformly once we do," and Kibana removes future integration work if AF-10 ever grows into a real dashboard.

When this recommendation flips
If the team's primary operational skill is already MongoDB-centric (existing DBAs/SREs, no ES experience), the operational-simplicity argument dominates and Mongo is the better real-world choice. Or if analytics is confirmed to stay frozen at "count only, forever" — in which case even the existing relational table with a maintained counter may beat both.
Doc 08Applies existing splits

Metadata Management at Scale

Question: "The metadata of the files" is ambiguous — structured link fields, or actual binary files?

Decision: Both, handled differently. Structured metadata (original URL, code, creator, timestamps, alias) stays on the existing ShortUrl row — no new store, it just grows by row count, served behind the same Redis cache as the redirect lookup. QR-code images (optional/stretch, if ever built) go to object storage (Azure Blob/S3-compatible), never a DB blob — keyed by short code, generated lazily on first request rather than for all 5M links/day unconditionally, and fronted by the same CDN as the redirect path.

Lifecycle

Soft-delete (IsDeleted/DeletedAtUtc) confirmed unchanged at 5M+ rows/day — it's a WHERE predicate on an indexed column, not an operation whose cost grows qualitatively with table size. Orphaned QR objects age out via passive Blob lifecycle policy rather than eager deletion, mirroring the relational soft-delete philosophy.

Explicitly deferred: metadata search/filter by creator (e.g., "show my links from last month") — flagged as a considered-but-undesigned gap, likely a composite relational index if ever built, not an ES commitment.

Doc 24Adopted

Batching Click/Stat Recording via a Redis Staging Counter

Question: At up to 100M fetches/day, how do we record "a click happened" without a durable-storage write on every single fetch?

Decision: Redis HINCRBY on a time-bucketed Hash key (stats:clicks:{unixTime/15}, field = short code) on every fetch — a second, functionally distinct Redis role from the lookup cache in Doc 07, with its own instance/DB-index and a noeviction policy (an evicted unflushed counter is silent data loss, unlike a cold cache miss). Flushed to SQL Server every 15 seconds as one batched UPDATE across every touched code, via a grace-period bucket-read that avoids any explicit atomic-swap primitive.

Durability trade-off, stated plainly
If Redis crashes between flushes, unflushed increments are lost — ClickCount becomes approximate (under-counts, never over-counts). Accepted because AF-09 explicitly scopes click count as a "nice to have," not a billing input or security signal. AOF persistence narrows but does not eliminate the loss window.

Complementary, not redundant, with the broker→Elasticsearch pipeline (Doc 25): that pipeline remains the system of record for the detailed per-click event; this counter is only a fast, approximate, rebuildable derived cache of the aggregate number.

Doc 25Adopted

Elasticsearch Bulk API for Click/Analytics Event Indexing

Question: Given the store (ES) and delivery mechanism (broker) are already decided, how should the consumer actually write events in?

Decision: Bulk API, not single-document indexing — the analytics-indexing Worker Service accumulates events in an in-memory buffer and flushes via _bulk on a size-or-time trigger: 1,000 documents OR 1 second, whichever comes first. Single-doc indexing at this volume would require ~1,150–12,150 individual HTTP calls/sec — arithmetically impossible through the 20-slot Elasticsearch bulkhead already sized in Doc 19.

LoadSingle-doc calls/secBulk requests/sec
5-yr sustained average~1,150–1,215~1–2
5-yr peak burst~6,100–12,150~6–12

Backpressure: a bounded in-memory buffer (5,000–10,000 events); once full, the consumer stops pulling from the broker rather than growing memory unboundedly — the broker (already durable) absorbs the backlog, not process memory. Partial failure: the _bulk response is parsed per-item — only the failed subset is retried or dead-lettered, never the whole batch, and broker offsets commit only for what Elasticsearch actually accepted.

Caching & Edge Delivery

Making the redirect path — the single highest-volume operation in the system — as cheap as possible to serve, ideally without most traffic ever touching the origin at all.

Doc 06Adopted — layered exception to v1

Output Caching, BFF, and CDN for the Public Redirect API

Question: How do we get redirect throughput up without silently reintroducing the staleness problem v1's 302-not-301 decision was specifically designed to prevent?

Decision: Three layered techniques, each with a deliberately short, bounded TTL — turning "never see the origin again" (301's failure mode) into "see the origin again within N seconds":

LayerMechanismTTL
ASP.NET Core Output CacheWhole-response cache, keyed by shortCode only10 seconds, plus proactive eviction on deactivation
BFF splitRedirect endpoint gets its own deployable — no auth middleware, minimal dependency graph, independently scaled—
Cloudflare CDN edge cacheCache Rule on the redirect route + origin Cache-Control: public, max-age=3030 seconds
Explicit exception to v1, stated for the record
v1's fn-fetch.md §10 chose 302 specifically so every access hits the origin, guaranteeing real-time expiry/deactivation enforcement and exact analytics counts. This document knowingly trades that guarantee: a deactivated link can keep resolving from edge cache for up to ~30 seconds, and analytics undercounts by roughly the CDN's cache-hit ratio (commonly 80–95%+). Accepted in exchange for absorbing the large majority of 100M/day traffic before origin. Cloudflare Logpush is named as the required companion reconciliation mechanism for exact counts.

Why 10s and 30s, not longer: a 10-second TTL is enough to collapse a viral burst to roughly one origin hit per 10 seconds for that code — the overwhelming majority of the available benefit; going to 60s buys little more origin-load reduction while multiplying staleness 6x. Same diminishing-returns logic sets the CDN tier at 30s, deliberately looser than the origin tier since it sits further from the source of truth.

Doc 07Adopted — like-for-like upgrade

Redis-Based Distributed Caching for Frequently-Accessed Short Codes

Question: Why does v1's per-instance IMemoryCache break once the API runs as many horizontally-scaled instances?

Decision: Swap IMemoryCache for a shared, managed Redis tier behind the same IShortUrlRepository Decorator abstraction v1 already used — same interface, same cache-aside pattern, only the backing store changes. Fixes two problems that get worse with fleet size: hit rate degrading roughly by a factor of N (every instance re-learns the same hot set independently), and invalidation only clearing the instance that handled the write (others serve stale data until TTL).

What would actually justify Kafka
Not throughput — replay (rebuilding the ES index from scratch without re-deriving from the OLTP store) and independent consumer groups added over time that need retroactive history (a fraud-detection service added 18 months from now). Neither is a near-term requirement today.

Honest cost of choosing Kafka anyway: self-managed Kafka needs partition/replication planning, broker sizing, consumer-lag/ISR monitoring, and genuine Kafka expertise on the team — a standing multi-person operational responsibility, not a one-time setup.

Background Job Hosting: Worker Service vs. Azure Functions

Question: Should background/async work run as a long-running .NET Worker Service or Azure Functions?

Decision: Split by workload shape, not one winner. Two genuinely different shapes exist in this system:

WorkloadHosting modelWhy
Analytics-indexing consumer, cache-invalidation subscriber, outbox relay (if built)Long-running Worker Service (containerized BackgroundService)Continuous, ~1,200/sec sustained, stateful consumer-group connections — never idle, so never realizes serverless's core value; cheaper as a fixed-baseline container at this volume
Retention-cleanup sweep, reconciliation sweepAzure Functions (Timer-triggered, Consumption plan)Minutes of work, a few times/day — a dedicated always-on container would pay ~99% of its cost for idle time
The cost crossover, quantified
At ~1,200 events/sec sustained 24/7, a Consumption-plan function is functionally never idle — it never scales to zero, so it pays the serverless per-execution premium the entire time while getting none of serverless's elasticity benefit. A long-running worker's cost, by contrast, is fixed once sized and improves per-event as throughput grows.

Consumer-group/offset semantics are also a poor fit for a per-invocation model — the Functions host ends up running something structurally equivalent to a long-lived consumer underneath the serverless label anyway, just with less visibility and control.

Resilience Patterns

Seven documents, each covering one resilience mechanism in isolation with its own concrete tuning numbers — deliberately not merged into one mega-document, because each has genuinely different numbers worth calling out on its own.

Doc 12Adopted

Distributed Rate Limiting for a Horizontally-Scaled API

Question: Why does v1's in-memory RateLimitPartition.GetFixedWindowLimiter break once the API runs as N instances?

Decision: With N instances each enforcing the same limit independently, a caller spreading requests across instances gets up to N× the intended limit. Fix: move the counter to Redis-backed sliding-window counters (not token bucket — a pure fixed-window or token-bucket allows boundary/idle bursting, exactly the scripted-bulk-creation abuse pattern this control exists to close), implemented as a custom PartitionedRateLimiter inside the existing Microsoft.AspNetCore.RateLimiting middleware.

Fetch/redirect fails open — redirect availability is named specifically in ANFR-01/ANFR-05, and refusing redirects because the rate limiter is down is a worse outcome than temporarily under-enforcing an abuse control.

Timeout Pattern for Outbound Calls

Question: Why does every outbound call need an explicit timeout, not just the one v1 already had?

A dependency that is slow is worse than a dependency that is down — a down dependency fails fast; a slow one hangs, exhausting the thread pool and connection pools far faster than raw load would, and shows up as creeping tail latency instead of a clean, alertable failure.

Connection timeout (can I even reach it) and operation timeout (did it answer fast enough) are tracked as two distinct bounds, both tighter than client-library defaults.

Doc 15Adopted

Retry Pattern for Extreme-Scale Dependencies

Question: Given an attempt failed, should there be another attempt at all, and under what bound?

Decision: Retry only transient failures — network errors, 5xx, timeouts. Never retry deterministic failures — 4xx validation, duplicate-alias 409, a definitive moderation "flagged" verdict (retrying just delays telling the caller the truth). Budget: 2–3 retries (3–4 total attempts) per call, dependency-dependent.

Idempotency is the precondition for retrying writes
Reads retry freely — no side effect to duplicate. Writes retry only when naturally idempotent (an ES upsert) or guarded by the idempotency-key mechanism in Doc 11. Otherwise a failed write surfaces to the caller rather than being silently retried.

A fleet of instances each independently retrying against a struggling dependency is a self-inflicted denial-of-service — retry amplification can exceed the load that degraded the dependency in the first place, and unbounded retry also delays the circuit breaker (Doc 18) from ever tripping.

Doc 16Adopted

Exponential Backoff for Retry Delays

Question: With no delay between retries, why does a struggling dependency get worse, not better?

delay(attempt) = min(base × factor^(attempt−1), cap)
Base
100 ms
Factor
2× (doubling)
Cap
30 s

A delay-free retry policy means every in-flight request across every instance fails at roughly the same instant and retries immediately — the dependency has to absorb roughly double its normal load the moment it's least able to, potentially extending the outage rather than letting it clear (a metastable failure state). The 30s cap is a safety rail for the patient, decoupled async paths (outbox relay, cache-invalidation subscriber) — synchronous calls (moderation check, cache-then-DB fallback) exhaust their small attempt budget at the 100/200/400ms rung, well inside a 5s window, long before the cap matters.

Doc 17Adopted — Decorrelated Jitter

Jitter

Question: Backoff makes each caller retry less often over time — so why do hundreds of instances still hammer a recovering dependency in synchronized waves?

Because every instance computes the same deterministic curve from the same trigger moment — all attempt-3 retries land at the same ~800ms mark, fleet-wide. The dependency recovers and immediately absorbs the entire backlog at once (thundering herd), often re-tripping it in a flap cycle.
StrategyFormulaWeakness
Full Jitterrandom(0, exp_value)Can draw two small delays in a row — near-instant repeated retries
Equal Jitterexp/2 + random(0, exp/2)Less spread than Full Jitter
Decorrelated Jitter (chosen)random(base, prev_delay × 3), floor = baseSlightly more code (stateful) — worth it at this fleet size

Decorrelated Jitter's floor at base means no attempt is ever near-instant after the first, and the ×3 multiplier keeps the ceiling trending upward — preserving exponential backoff's useful shape while still breaking fleet-wide lockstep. Implemented via Polly's UseJitter = true on the exponential curve.

Circuit Breaker

Question: What do retry/backoff/jitter not solve — a dependency that is genuinely down, not transiently slow?

Decision: Polly's CircuitBreakerStrategy per dependency — a rolling sample window with a failure-ratio threshold, not "N consecutive failures" (which breaks down under concurrent load). Worked example: the Elasticsearch analytics-query call, chosen because its fallback is cheap and safe (serve stale cached count, or omit the field) — the core redirect path never touches ES at all.

Sampling window
30 s
Min throughput
20 calls
Failure ratio
50%
Break duration
30 s

Trip condition, one sentence: if at least 20 calls occur in a rolling 30s window and 50%+ fail, the circuit opens for 30s, then half-opens with a small trial-call budget before fully closing or reopening.

Fallback is dependency-specific — the load-bearing design decision
ES: serve last cached count, tagged stale, or omit the field (HTTP 200, never fabricate a 0). Redis cache: bypass and read primary DB. Primary DB: no safe fallback for writes — fail fast, don't fabricate success. Message broker: cannot silently drop (data loss) — buffer/spool or reject with retry guidance. Moderation check: fail the create with a clear 503, never "allow-all while open."
Doc 19Adopted

Bulkhead Isolation for Shared Resource Pools

Question: Why can a slow Elasticsearch or moderation-check call take down the completely unrelated, highest-priority redirect path?

Because they all share the same process: the same CLR thread pool, the same default connection limits. Without a hard ceiling, outstanding calls to a slow dependency accumulate faster than they drain until they exhaust a shared, finite resource — and this is invisible in the failing dependency's own health metrics. Elasticsearch can report degraded-but-not-down while the redirect path's latency spikes for a completely unrelated reason.
CompartmentStarting concurrency ceiling
Redirect path — DB/cache reads200
Create path — DB writes50
Moderation-check HTTP client10 — deliberately tight
Elasticsearch indexing20
Redis — rate-limit counters50

Implemented via Polly's AddConcurrencyLimiter (the modern replacement for the legacy Bulkhead policy) or a SemaphoreSlim-based gate for non-HTTP dependencies. A small bounded queue sits beyond the ceiling; once that's also full, requests are rejected immediately with 503 rather than piling up — a large queue only delays the same resource exhaustion, it doesn't prevent it.

Complements, doesn't overlap with, Circuit Breaker
Bulkhead caps how many calls run regardless of outcome; circuit breaker decides whether to attempt at all based on failure history. Needed together: without a breaker, a bulkhead's small pool can be permanently saturated by calls guaranteed to fail; without a bulkhead, a healthy-but-slow dependency under legitimate load can still exhaust shared resources since it never trips a failure-based breaker.

Security at Extreme Scale: Reputation, Attack Surface, and Authorization

Question: What breaks specifically at scale that v1's security baseline didn't need to address?

1. Domain reputation — a shared, poisonable resource

A constant false-negative rate on the creation-time domain check stops being noise at volume: 0.1% of 5M/day is ~5,000 uncaught bad links created per day, every day. Worse, the check runs once at creation — a domain that's clean at creation and compromised weeks later ("domain drift") is invisible by construction. Reputation blocklisting is not proportional to abuse: ~50 flagged links can get the entire domain blocklisted, breaking every other legitimate link simultaneously.

MitigationMechanism
Continuous re-scanningTiered cadence — high-click links daily, new links daily for 7 days, long tail monthly
Fast automated takedownImmediate deactivation on a post-creation flag, propagated through every cache layer
Domain-reputation monitoringHourly checks against Safe Browsing/SmartScreen, wired into the observability alert set

2. Attack-surface issues introduced or amplified by v2's topology

  • Distributed enumeration: per-IP limits (Doc 12) do nothing against a scan spread across thousands of IPs each individually staying under threshold. Named as a genuine, unsolved gap — the fix is aggregate 404-rate anomaly detection, not a bigger Redis counter.
  • DDoS on redirect: the Cloudflare CDN (Doc 06) is stated explicitly as this system's primary DDoS absorption layer, not just a performance optimization; origin-level rate limiting is the second line of defense.
  • Broker/consumer injection risk: the API boundary's input validation does not extend automatically past the producer — every Kafka/broker consumer is a new trust boundary and must independently validate deserialized payloads.

3. Authorization — more enforcement surfaces, not fewer

The concrete leak scenario
AF-10's analytics API is creator-only. Once analytics data moves to Elasticsearch (Doc 03), that scoping is not inherited automatically — an ES aggregation query that omits a term filter on the owner returns every creator's data, and nothing about the query fails or looks incomplete. This is exactly the kind of gap a single-database v1 system structurally could not have.

Recommendation: centralize authorization in the Application layer, before any data-store query is issued — relational or Elasticsearch — never relying on a downstream store's own access control as the sole enforcement point.

Explicitly out of scope

Full pen testing, WAF rule specifics, formal certification (SOC 2/ISO 27001), the actual auth/authn mechanism (v1's mock is not resolved here), vendor selection, and a concrete anomaly-detection implementation.

Observability at Extreme Scale

Question: Why does v1's liveness/readiness-endpoint model stop being sufficient?

v1 has exactly one place a request can be — one process, one local database. v2 removes every one of those simplifying assumptions: multiple API instances, a distributed cache, an async event pipeline, a separate analytics store. Grepping one instance's log cannot answer "which of these five components is the bottleneck for this one request," because nothing ties the log lines together. Observability is making the request path traceable as a graph, not a line.
Tracing

OpenTelemetry .NET SDK, W3C Trace Context propagation. The hard part v1 never had: propagating trace context across the async broker boundary — the producer attaches traceparent to message headers, the consumer extracts it and starts a child span, not a new root trace, so one trace ID connects "API received request" through "consumer picked it up 400ms later on a different machine" to "document indexed into Elasticsearch."

Metrics — the cardinality rule
Never tag a metric with an unbounded per-entity value
Tagging by raw short code, user ID, or IP creates a new time series per code — millions of them — the classic "cardinality explosion" that destroys a metrics pipeline. Aggregate by endpoint, status class, cache hit/miss, consumer name instead. Per-entity questions belong to traces and logs, not metrics.

Core metric set: request rate, per-endpoint p50/p95/p99 latency histograms (never pre-averaged), cache hit rate, queue depth/consumer lag, error rate.

Alerting — 5 SLO-driven Grafana Alerting rules
  1. Redirect p99 latency SLO burn (sustained window, not single breach)
  2. Redirect p95 warning (earlier heads-up before the p99 alert)
  3. Cache hit-rate drop (leading indicator before latency degrades)
  4. Consumer lag growth (threatens the "seconds not minutes" invalidation guarantee from Doc 07)
  5. Error rate spike (general-purpose backstop)
Tooling

OpenTelemetry SDK for instrumentation, exporting via OTLP to a Grafana stack — Loki (logs), Tempo (traces), a Prometheus-compatible store (metrics), Grafana (dashboards/alerting). Named honestly as separate infrastructure from the Elasticsearch analytics cluster — a real, additional operational cost, chosen because Loki's label-only indexing is materially cheaper at this log volume than full-text-indexed logs, and the stack has a strong Kubernetes-native operational story. Elastic Observability and Application Insights are named as legitimate alternatives if minimizing platform count or Azure-managed hosting is the priority instead.

AI Pluggability and Vector Readiness

Question: Can URLs and metadata be optionally represented as vectors later, without a redesign?

Decision: Yes, and the mechanism already exists for reasons unrelated to AI. Where embeddings would be generated: a new, independent AI-enrichment consumer subscribing to the existing UrlCreated broker event (Doc 05) — off the hot path entirely, touching nothing in the create/fetch write path. Where vectors would live: Elasticsearch's native dense_vector field + k-NN support — explicitly not a dedicated vector database (Pinecone, Weaviate, Milvus), since nothing in this system's realistic use cases (similarity search over its own link corpus, not a general-purpose embedding product) approaches the scale/recall profile that would justify paying the operational cost of a second specialized store.

"metadataEmbedding": {

  "dims": 768,          // illustrative — depends on the (unselected) embedding model

  "similarity": "cosine"

The field is nullable and additive — a document with no vector is a completely normal document; every existing query is unaffected.
