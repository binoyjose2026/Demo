Engineering Approach

Why this project was built the way it was — a reflection on the sequencing, written for anyone reviewing the finished work.

The overall shape of the approach

The shape of this project is deliberately lopsided: a large amount of AI-assisted architectural exploration happened before almost any code was written, and what shipped afterward is a small, intentionally non-scalable MVP. That is not the order you'd get by accident, and it isn't a sign the implementation was rushed or under-baked. It's a conscious choice about where the effort actually belongs. Code that solves a problem the system doesn't have yet is wasted code; reasoning about a problem the system might eventually have is cheap, especially with AI assistance to run many independent explorations in parallel. So the investment went where it compounds — into the thinking — and the implementation was kept to exactly what a working prototype needs, no more.

What the design phase actually covered

Three stages, each narrowing the problem before the next one started.

Requirements

The starting point was a raw brief, which got turned into formal functional and non-functional requirement documents. Rather than treating those documents as settled, they were explicitly pressure-tested from a product-owner's point of view: a dedicated review pass surfaced roughly 37 open product questions — who owns a link, what its lifecycle looks like, what limits and abuse policy should apply, what the business model even is, what compliance obligations exist, what SLAs are implied. Those questions got answered deliberately, before anything downstream assumed a particular answer, and the resulting decisions locked the actual v1 scope. That sequencing matters: it's the difference between building against a guess and building against a scope that was actually interrogated first.

v1 design

With scope locked, the v1 design pass worked out a full architecture for a working system: a layered solution structure, the repository pattern, SQLite plus EF Core as the embedded datastore, and SOLID-principle-driven design throughout. That design covered security, scalability, performance, resilience, reliability and availability, unit testing, and integration testing — plus the three core functional flows the product actually needs: create, fetch, and analytics. This is the architecture a straightforward, correctly-built v1 service would follow.

v2 design — "what would extreme scale actually require"

The third stage asked a different, deliberately broader question: not "what does v1 need," but what would this system have to become if it actually had to handle real growth — millions of creates a day scaling toward tens of millions, tens of millions of fetches a day scaling toward hundreds of millions, over a five-year horizon. That review produced 29 documents spanning data partitioning, Elasticsearch versus alternatives for analytics storage, caching and CDN strategy, messaging, the full resilience-pattern family (timeout, retry, backoff, jitter, circuit breaker, bulkhead), security at scale, Kubernetes-based infrastructure, and forward-looking AI-pluggability. The full write-up, with the numbers and verdicts behind each decision, is at the v2 Scalability Design Review.

The important nuance: v2 was a "what if," not a build list

It's worth being explicit about this, because it's easy to misread 29 documents of extreme-scale architecture as a to-do list. It wasn't. Every document in that review is framed as an exploration of what extreme scale would require if it happened — not a claim that v1's simpler choices were wrong for their context, and not an instruction to go build all of it now.

It also wasn't a rubber stamp of whatever technology sounds impressive. Several of the v2 documents concluded that a popular, expected choice was actually not justified at the system's stated scale, and said so with real math instead of leaning on industry-standard advice:

Not adopted by default

Kafka

Worked out against this system's own five-year projection, the event-publishing throughput lands at roughly 0.1–1% of a single Kafka broker's real capacity. Standing up a Kafka cluster to carry that little traffic is operational cost with no matching benefit, so a simpler managed queue was recommended instead — with Kafka named explicitly as the upgrade path if replay semantics or multiple independent consumers ever become a real need.

Not adopted

Outbox pattern

Evaluated for the create flow's event publication and rejected, with the reasoning shown rather than asserted: the only durable write on that path is a single local database transaction with no broker involved, so the dual-write problem the Outbox pattern exists to solve was never actually present.

Not adopted

Saga pattern

Also evaluated and also rejected for the create flow: create is one write to one database with one atomic commit, not a multi-service transaction, so there is nothing for a Saga to coordinate or compensate.

This is the actual evidence of engineering judgment on display in this project — not the volume of documents, but the willingness to reason from the system's real shape and real numbers, and to say "no, not this" about tools that are usually reached for by default. Resisting the reflexive pull toward the impressive-sounding option is harder than adopting it, and it's the part that's easy to skip if the goal is just to look thorough.

Why the final shipped MVP (v3) is deliberately minimal and not scalable

What actually shipped scopes down to the two endpoints that matter for a working prototype — create and fetch — running on SQLite, with a null/no-op cache placeholder standing in for a real caching layer. This is explicitly not the extreme-scale architecture described in v2, and that gap is intentional, not an oversight.

Building v2's infrastructure — sharded storage, Elasticsearch, a message broker, a full resilience-pattern stack, Kubernetes — for a prototype that doesn't carry that traffic would be premature engineering effort spent on a problem the system doesn't have yet. Knowing when not to build something is as much a part of engineering judgment as knowing how to build it.

Rather than quietly dropping the enterprise-grade concerns v2 surfaced, the MVP code leaves them as clearly-commented, honest placeholders sitting at their exact plug-in points:

  • A null Kafka event-publisher seam, with the real producer call left commented-out in place, ready to be swapped in.
  • A rate-limiting policy that exists in the code path but is currently disabled.
  • An authorization policy that is present but bypassed rather than silently omitted.
  • An idempotency-key seam, matching the design already worked out in the v2 review, not yet wired to a real store.

Each of these placeholders points back to the specific v2 document where the full design already exists, so the distance between what's built and what's been thought through is documented, not hidden. Anyone reading the code can see exactly what was deferred and why, and exactly where to pick it back up.

The throughline

Most of the actual engineering value in this project is in the reasoning, not the code volume: decomposing the problem, pressure-testing assumptions instead of accepting them, and working through real trade-offs with real numbers rather than received wisdom. AI-assisted parallel exploration is what made it economical to do that reasoning this thoroughly — 29 independent documents, each demanding its own numbers and its own honest verdict — while still shipping a working, minimal, defensible prototype in the time actually available. The two halves depend on each other: the MVP is small because the thinking that justifies keeping it small was already done, and written down.
